## 1. 目标

在推流端（WHIP/WebRTC，H.264 为主）对无用背景做感知抑制，把带宽尽量倾斜给高速运动的核心业务区域（抽奖机彩球区）：

1. 编码前加强力时域降噪，压平静止背景的传感器噪点（噪点是码率杀手）；
2. 编码时按区域动态调整量化参数（QP）：彩球区低 QP（高质量），背景墙高 QP（强压缩）。

## 2. 结论摘要

**方案整体可落地，且编码器侧不需要任何改动。**

- **ROI 动态 QP：OBS 29.1+ 已内置完整的编码器 ROI API**，本代码库（32.1.2）中 x264 / NVENC / QSV / AMF 四家编码器全部实现了 ROI → QP 映射。要写的只有"往编码器塞 ROI 矩形"这一小段逻辑（Lua 脚本或 WHIP 补丁均可）。
- **时域降噪：OBS 无内置视频降噪滤镜**，需要移植 FFmpeg 的 `hqdn3d` 为 OBS 滤镜插件（约 300 行，许可兼容）。`nlmeans` 因性能不可行直接排除。
- 修正一个设想：降噪强度**不能开"极强"**——强时域降噪会让高速运动的彩球拖影，恰好毁掉最想保的区域。正确做法是中等强度全帧降噪，或（更优）利用已有的 ROI 矩形做"掩膜降噪"：背景强降噪、彩球区旁路。

关键 API 语义（`libobs/obs-encoder.c:1988`）：

- ROI 矩形最小 16×16，坐标以**该编码器输入分辨率**为准；
- 多个 ROI 重叠时，**先添加的优先**（`obs.h:2310` 注释）；
- `obs_encoder_clear_roi()` 清空后可重设，支持运行时动态更新。

## 4. 实施方案

### 阶段一：静态 ROI（约 1 天，收益大头）

抽奖机机位固定，**一个静态矩形框住透明滚球罩即可拿到约九成收益**。QP 图粒度是 16×16 宏块，逐球跟踪没有意义。

添加顺序（利用"先加优先"规则）：

1. 先加彩球区：`priority = +0.2 ~ +0.4`（起步值，调参用）；
2. 再加覆盖全帧的背景区：`priority = -0.2 ~ -0.3`。

**priority 不要拉满**：x264/NVENC 的换算是 `ΔQP = -51 × priority`，`priority = 1.0` 等于 QP 直降 51，属于极端值。

落地实现（已完成，跳过 Lua 验证直接原生）：

- `whip-service.cpp` / `whip-service.h`：ROI 属性组 + 默认值（`Defaults()`），出现在 设置 → 直播 的 WHIP 服务表单里；
- `whip-output.cpp` / `whip-output.h`：`WHIPOutput::ApplyRoi()`，在 `Start()` 的 `obs_output_initialize_encoders` 成功后调用；每层编码器先 `clear_roi`（清掉上次会话残留），再按该层 `obs_encoder_get_width/height` 与输出分辨率的比例换算矩形（外扩取整，不会因取整缩小覆盖区），先加高优区、后加全帧背景区；应用结果打 INFO/WARNING 日志。

### 阶段二：hqdn3d 时域降噪滤镜（已实现）

- **排除 nlmeans**：FFmpeg CPU 实现 1080p 仅个位数 fps，实时推流不可行。
- **实现**：`plugins/obs-filters/temporal-denoise-filter.c`，滤镜 ID `temporal_denoise_filter`（界面名"时域降噪"）。hqdn3d 时域分量的逐字节移植（空域分量刻意省略）：16-bit 累加器（8 位小数）+ 相似度加权 LUT，一阶递归低通；逐像素处理使其与内存布局无关——平面（I420/I422/I444/Y800）、半平面（NV12，UV 交织无碍）、打包 4:2:2（YUY2/UYVY/YVYU，按字节奇偶选亮度/色度 LUT）、RGB（RGBA/BGRA/BGRX，逐字节）全部支持；不支持的格式（10-bit 等）直通并告警一次。
- **运动自适应**：相似度曲线使大帧差的系数趋零、直接透传，运动内容不拖影，静止区噪点被压平（这正是耗码率的部分）。
- **边界处理**：LUT 系数按差值桶中点计算，极亮/极暗处可能轻微过冲，已在 `lowpass8` 钳位到 `[0, 255<<8]`，否则字节转换会回绕（白区冒黑点）。
- **参数**：亮度/色度强度滑杆 0~20，默认 6.0 / 4.5。分辨率/格式变化时自动重建状态并以当前帧播种（首帧直通）。
- **用法**：右键摄像头源 → 滤镜 → 添加"时域降噪"。挂在 async 源的 CPU 帧路径上，零拷贝就地处理。
- 后续可选：HLSL/GPU 版（需历史帧纹理）；检测矩形旁路掩膜（见阶段三）。

### 阶段三：动态检测（球体 + 人物）→ 动态 ROI（v1 已实现：零依赖运动检测）

需求（Greg）：识别出的球体区域和人物区域就是 ROI。原始需求允许"极轻量级算法（或 OpenCV）"两条路；公开库不宜引入 OpenCV + DNN 模型的重依赖，**v1 采用零依赖运动检测**（球在滚、人在动、背景墙不动 → 运动即 ROI），编码器侧接口与检测算法解耦，后续可在私有构建里换成 OpenCV 检测器而不动应用路径。

已实现（`plugins/obs-webrtc/motion-roi.cpp/h`，`MotionRoiDetector`）：

- **取帧**：`obs_add_raw_video_callback2` 拿合成后的节目画面（编码器看到的同一画面，无需场景坐标换算），请求 320×180 I420、帧率 1/3 分频——libobs 负责缩放，处理成本 <1ms/帧。
- **检测**：8×8 块网格（40×23），隔像素采样，**双重判定抗舞台动态灯效**（现场确认有动态灯效后加入）：
  - 亮度门：逐块平均绝对帧差，先减去全帧平均亮度偏移（全局补偿，抵消自动曝光/总控调光），阈值 6；
  - 结构门：每个采样点记录与上下左右邻居的相对明暗关系（census code，±8 死区），比较两帧间比特翻转率，块内翻转 ≥ 0.4 位/采样点才算结构变化。光照只改亮度不改结构（扫光打在静止树木上不触发），物体移动才翻转结构位；
  - 两门同开才激活；块激活后保持 ~1s（HOLD_TICKS=20）防止球弹跳间隙/人短暂静止导致闪烁。
- **聚类**：4 连通 BFS 连通域，滤掉 <2 块的噪点，取最大的至多 4 个包围盒（球区和主播自然分成独立矩形）。
- **应用**：矩形按各 simulcast 层分辨率换算，先加正优先级矩形、再加全帧负优先级背景；仅在块级矩形变化且距上次 ≥200ms 时才更新（`roi_increment` 缓存保证无谓开销为零）；优先级复用服务设置的 `roi_priority`/`roi_bg_priority`（默认 +0.3/−0.25）。
- **开关联动**：`detect_roi`（设置 → 直播 → 高级选项"球体区域和人物ROI"）开启且手动 ROI（`roi_enabled`，调试用）关闭时启动检测器；手动 ROI 优先于检测器；推流停止时检测器同步停止。
- **成本注意**：raw video 回调会迫使主混合画面 GPU→CPU 回读（x264 本来就走这条路；纯 NVENC 机器新增少量 PCIe 带宽与 swscale 缩放开销）。

后续可选升级（按需）：

- **OpenCV 精确检测**（球体颜色阈值/霍夫圆 + 人物 DNN）：替换 `MotionRoiDetector` 的检测部分即可，编码器应用路径不变；建议放 ppobs 私有构建，避免公开库背依赖。
- **掩膜降噪联动**：检测矩形喂给时域降噪滤镜做旁路掩膜——背景强降噪、球/人区域旁路。

## 5. 风险与注意事项

1. **CBR 语义**：ROI 只改码率分配，总码率不变。WebRTC 拥塞控制下调码率时，背景会最先块状化——这符合预期，但需向业务方说明背景观感会明显劣化。
2. **Simulcast 一致性**：每层独立设 ROI，坐标换算错误会导致低分辨率层 ROI 错位；脚本/补丁里必须按层分辨率缩放。
3. **编码器切换**：ROI 依赖 `OBS_ENCODER_CAP_ROI`，本库 x264/NVENC/QSV/AMF 均支持；若未来接入其它编码器需确认 caps。
4. **降噪拖影**：强时域降噪对高速彩球有拖影风险，务必从中等强度起步并肉眼验收彩球运动清晰度。
5. **AV1/HEVC 粒度**：NVENC 下 HEVC 为 32×32、AV1 为 64×64 块，ROI 边缘会更粗，彩球区矩形建议外扩一个块的余量。

## 6. 验证方案

- 同码率录制两路（ROI 开/关），裁剪彩球区计算 VMAF / PSNR 对比；
- x264 日志可直接观察 QP 分布变化（`avg QP` 及分区统计）；
- 低码率压力测试（如 1.5 Mbps 1080p）下人工验收：彩球可辨识度 vs 背景劣化程度；
- 降噪滤镜单独 A/B：关 ROI 只开降噪，观察同码率下编码器给运动区的实际分配是否上升（x264 log / `obs_encoder` 统计）。

# 抗灯效版检测器已实现并编译通过

回顾一下"方案 1 + 方案 2"分别是什么、以及现在代码里的样子：

**方案 1 = 全局亮度补偿**。每帧先算整幅画面的平均亮度相对上一帧变了多少（比如总控调光让全场暗了 15），每个块做帧差判断前先把这个共同偏移减掉。它抵消的是"全画面一起变"的干扰：相机自动曝光、整体调光。

**方案 2 = census 纹理结构比较**。每个采样点记一个 8 位编码：它和上下左右四个邻居谁亮谁暗（带 ±8 的死区，平坦区域不受噪声影响）。两帧之间比较这个编码翻转了多少位。原理是**光照只改变亮度、不改变纹理结构**——扫光打在树上，树叶和背景的明暗关系原封不动，编码不翻转；彩球滚过来盖住树叶，这个位置的明暗关系真的变了，才翻转。

**组合规则是"与"逻辑**：一个块必须同时通过两道门才算运动——

1. 亮度门：补偿后的平均帧差 ≥ 6；
2. 结构门：census 位翻转率 ≥ 0.4 位/采样点。

扫光扫过静止树木：亮度门开、结构门关 → 不触发。球滚/人动：两门全开 → 触发。全场调光：亮度门都开不了（被补偿掉）。

已在 [motion-roi.cpp](plugins/obs-webrtc/motion-roi.cpp) 落地，`obs-webrtc.dll` 重新编译并复制进 rundir，成本仍远低于 1ms/帧（320×180 采样网格上两遍整数运算）。

**实测时如果发现两类偏差，各有一个对应旋钮**：
- 灯效仍有误触发（比如非常锐利的光斑边缘本身就是移动的"结构"——硬边光斑在物理上确实是移动图案，census 也会如实报告）→ 调高 `CENSUS_NUM/DEN`（现在 2/5，改 3/5 更严格）；
- 反过来漏检（低对比场景下球和背景颜色接近）→ 调低到 1/5 或放宽 `CENSUS_MARGIN`。

一个诚实的边界说明：census 能免疫的是**渐变式**光照（扫光、调光、频闪的亮度包络）；如果灯效是**带锐利边缘的图案投影**（比如 gobo 图案灯在树上投出移动的斑纹），那在任何算法看来都是真实移动的纹理，只能靠调严阈值或现场控灯规避。这类灯效如果你们现场有，实测阶段重点看它。
