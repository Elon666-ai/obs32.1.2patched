# OBS 人脸风格化直播方案：ONNX Runtime 滤镜

> 状态：端到端管线代码已实现（检测 → 稳定 → 对齐 → 风格生成 → 回贴），
> 但**尚未用真实模型验证过画质**——所有验证基于合成数据与契约校验。
> 性能数字仍待基准验证。
> 日期：2026-09-04
> 适用代码库：obs32.1.2patched
>
> 目标形态：视频滤镜 `face_swap_filter`（`plugins/obs-filters/`），挂在摄像头源上，
> 检测到人脸时用**风格生成模型**改写面部外观，无脸时直通。推理走 ONNX Runtime。

## 0. 方向变更记录（2026-09-04）

原方案基于 InsightFace `inswapper_128` 做**身份替换**。该方向已终止，原因：

1. InsightFace 已下架 `inswapper_128`，无官方获取渠道；
2. 原始许可证限定非商业研究用途，与直播推流的产品定位冲突；
3. 身份替换本身带来肖像权与平台合规风险（原 §9）。

**新方向**：使用自训练模型或许可宽松的公开模型（动物头像、卡通化等风格生成），
模型把目标外观编码在自身权重里，因此：

- 不需要源脸图片，不需要 ArcFace identity embedding，不需要 `emap` 投影；
- 模型契约简化为**单输入单输出**：`[1,3,128,128] → [1,3,128,128]`；
- 不涉及特定自然人身份，肖像权风险大幅降低。

已随之删除的代码：`face-swap-embedding.*`、`face-swap-emap.*` 及各自测试、
ORT 的双输入 `Run` 路径、源脸图片加载链路。

## 1. 目标与非目标

**目标**：在推流端实时改写主播面部外观，输出画面与正常摄像头画面在管线上完全等价（下游
编码、ROI、录制均无需改动）。

**非目标**：

- 不做身份替换（deepfake）。模型不接受源脸输入，无法指定"换成某个人"；
- 不做视频文件的离线批量处理（那是另一套架构，无实时性约束）；
- 不做表情驱动的虚拟形象（VTuber 方向的技术路径不同）；
- 不追求电影级融合质量。直播是流式实时场景，帧预算 10ms 量级，与离线逐帧精修不可比。

## 2. 结论摘要

**可落地，本库的滤镜架构已经具备承载它的全部条件，但推理运行时是必须新增的重依赖。**

- **OBS 滤镜接入路径已具备**：本 fork 已自研 `beauty-filter.c`（当前 893 行，使用
  `OBS_SOURCE_ASYNC` 的同步 CPU `filter_video` 路径）和
  `clarity-filter.c`，`face_swap_filter` 与它们同构，注册与挂载路径可直接复用。
- **推理运行时必须新增**：除文档与 NVIDIA Video Effects SDK 自身的 TensorRT 错误码外，
  业务源码没有 ONNX Runtime、OpenCV、NCNN 或 DirectML 推理设施可用。这是本方案的重量级新增依赖。
- **与美颜的本质差异**：`beauty-filter.c` 的人脸定位是启发式 CV（肤色连通域 + 暗区聚类找
  眼睛，见该文件头部注释），可以在视频线程里同步跑完。换脸必须跑神经网络，目标单次耗时
  见 §5，**必须与视频线程解耦**，否则会占用帧预算。这是两者架构上最大的分野。
- **硬件假设尚未完成可复现实测**：开发机为 RTX 4060 Laptop（8GB VRAM，算力 8.9 Ada），
  但推理、色彩转换、游戏、NVENC 同时运行时的预算必须通过独立基准和压力测试确认（见 §5）。

## 4. 架构设计

### 4.1 数据流

```
dshow_input (摄像头)
  └─ face_swap_filter
       │
       ├─ filter_video（视频线程，60fps，绝不阻塞）
       │    ├─ 无有效人脸 → 原样返回 frame（exact passthrough）
       │    └─ 有缓存结果 → 仿射变换回贴 + 边缘羽化 → 返回
       │
       └─ 推理线程（独立线程，限频 15fps）
            ├─ 取最近一帧的副本（letterbox 到 640×640）
            ├─ SCRFD 人脸检测 → 五点关键点 → 逆映射回原帧坐标
            ├─ 时域稳定（EMA + 跳变拒绝 + 淡入淡出）
            ├─ 五点相似变换 → 128×128 对齐 crop
            ├─ 风格模型前向 → 128×128 结果
            └─ 写入结果槽（含仿射矩阵 + 时间戳 + 尺寸）
```

**核心不变量**：`filter_video` 中不含任何推理调用、不含任何可能阻塞的锁等待。
视频线程只能复制当前帧到预分配的 latest-frame 槽，或在 `trylock` 失败时继续使用旧结果。
推理线程慢了只表现为
"贴合略滞后"，绝不表现为掉帧。

**帧与线程协议**：

- 输入帧不得把 `frame->data[]` 指针交给推理线程；使用 `obs_source_frame_create()` +
  `obs_source_frame_copy()`，保留各 plane 的 stride、timestamp、flip 和色彩元数据。
- latest-frame 槽采用单生产者/单消费者语义，槽的发布和取用必须有明确的 mutex/序列号协议；
  推理线程只能读取已发布副本，不能读取 OBS 所有的原帧。
- 结果槽的图像 buffer、mask、仿射矩阵、目标关键点和 timestamp 必须在同一发布操作中可见；
  `filter_video` 拿不到 try-lock 时继续使用上一份完整结果。
- `destroy` 的顺序固定为：设置 stop、唤醒 worker、join worker、释放 ORT session/模型/槽和锁。
  不允许 worker 在 `destroy` 返回后访问 filter data。
- 为避免每帧分配，P0 即预分配两份输入/结果容量；分辨率或格式变化时暂停处理、在安全点重建，
  期间直通。

### 4.2 推理运行时集成

**选型：ONNX Runtime，运行时动态加载，执行后端自动降级。**

优先级链：`TensorRT EP → CUDA EP → DirectML EP → CPU EP`。这是应用显式尝试的顺序，不是 ORT
自动保证的顺序。每个 EP 都需要加载对应 provider DLL、检查版本兼容性并创建 session；创建或运行
失败后销毁该 session，清理 provider 状态，再尝试下一个 EP。DirectML 仅在 Windows 可用。

- 开发机（RTX 4060）会命中 TensorRT/CUDA，性能最优；
- AMD/Intel 用户降到 DirectML，仍可用；
- 全部失败则降到 CPU，或直接禁用滤镜（转直通）并打日志。

**必须走动态加载而非硬链接**，模式对齐 `nvvfx-load.h:283` 的函数指针表：
DLL 缺失时滤镜自动降级为直通 + 一行 WARNING，OBS 主体绝不受影响。这与 `nv-filters`
对待 NVIDIA SDK 的既有态度一致——第三方 AI SDK 是可选增强，不是硬依赖。

**模型清单**：

| 模型 | 文件名 | 契约 | 归一化 |
|---|---|---|---|
| 人脸检测（首选） | `yunet.onnx` | 输入 `[1,3,640,640]`；12 输出（cls/obj/bbox/kps × stride 8/16/32） | 原始 `0-255` |
| 人脸检测（备选） | `scrfd-500m.onnx` | 输入 `[1,3,640,640]`；9 输出（score/bbox/kps × stride 8/16/32） | `(pixel - 127.5) / 128` |
| 风格生成 | 用户选择的任意 `.onnx` | 输入 `[1,3,128,128]`，输出 `[1,3,128,128]` | 输入 `pixel / 255`，输出 `[0,1]` |

滤镜按上表顺序探测检测器，加载到哪个就用哪个对应的归一化与解码器。
**YuNet 优先，因为它是 MIT 许可、可商用**；SCRFD 仅作为兼容保留，其权重限非商业研究。

两者的解码差异不止于输出数量：YuNet 每格 1 个 anchor（SCRFD 是 2 个），置信度是
`sqrt(cls × obj)`（两者均已 sigmoid），bbox 为相对 anchor 的偏移且宽高取对数。
这些差异已由 `tools/verify_yunet.py` 对真实模型验证。

风格模型由用户从模型目录中选择，滤镜在加载时校验 shape、float32 类型和输入/输出数量，
不匹配即拒绝并保持直通。

**风格模型的来源与许可证由操作者负责**：自训练模型，或明确允许商用的公开模型。
本方案不内置任何模型下载器，也不随包分发模型——这是方向变更后的有意决定，
既回避了 §0 的许可证问题，也免去了签名 manifest、缓存管理和跨实例下载锁的工作量。

模型放置目录（不入 git）：

```text
%APPDATA%/obs-studio/face-swap-models/
```

## 5. 性能预算（基于开发机实测硬件）

开发机配置（`nvidia-smi` / WMI 实测）：

- GPU：RTX 4060 Laptop，8188 MiB VRAM，算力 8.9（Ada），驱动 555.97
- CPU：i7-13650HX，14 核 20 线程
- 内存：16GB

以下是待验证的目标预算，不是当前仓库的实测结论：

- 单次目标脸处理总计 **< 10ms**（检测、关键点、转换、换脸和拷贝均需计入）；
- worker 限频 15fps，GPU 时间占用和功耗影响以同步 GPU event 与系统指标实测；
- 显存峰值目标 < 400MB，但必须覆盖 ORT、provider、workspace、engine 构建和双缓冲。

基准必须记录模型版本、EP、输入尺寸、预热次数、P50/P95/P99、CPU/GPU 转换耗时、首次推理耗时、
显存峰值和并发 session 数。FP16 只有在所选 EP 确认支持并实际执行时才能计入预算；CPU fallback
不得假定 FP16 性能。

**主要待验证风险是共享 GPU 的功耗和调度竞争。** 这是笔记本，直播时 GPU 需同时承担：游戏渲染 +
NVENC 编码 + 换脸推理。4060 Laptop 的 TGP 受厂商限制（60-115W 不等），三者叠加可能表现为
游戏帧率下降、编码掉帧或推理延迟上升，不能预先断言只影响其中一项。

对策（P0 建立 CPU 墙钟与队列探针，P3 补齐 GPU/编码遥测和自动策略）：

1. 推理线程限频，默认 15fps，可调至 10fps；
2. 性能探针：记录单帧推理耗时、GPU 占用、编码器掉帧数，写入日志；
3. 动态降级：检测到编码掉帧则自动降低推理频率。

## 6. 关键技术点

### 6.1 无脸即直通

`beauty-filter.c:19-21` 的注释点明了这个契约为何重要——正因无脸时是 exact passthrough，
才敢对所有摄像头无差别挂载。换脸必须保持同一契约：未检测到人脸、模型未就绪、
运行时加载失败，三种情况一律原样返回 frame。

### 6.2 帧格式支持与色彩转换

对齐 `beauty-filter.c:178-219`：I420 / NV12 / YUY2 / YVYU / UYVY（dshow 摄像头的现实输出集合），
其余格式直通并打一次日志。`plane_view` 只能复用作 CPU 平面访问层；模型输入仍需显式完成 YUV→
RGB/BGR、full/limited range、矩阵、镜像/翻转、缩放、归一化和 stride 处理。输出必须按原始格式
和 stride 回贴，不能改变下游帧格式。P0/P1 要覆盖奇数尺寸、`frame->flip`、BT.601/BT.709、
full/limited range 和 NV12/I420 的测试样本。

### 6.3 时域稳定

`beauty-filter.c:27-35` 描述的稳定化策略（死区 + 慢速 EMA + 亚死区冻结 + 跳变拒绝 +
淡入淡出）对换脸只会**更加关键**：换脸的抖动是"整张脸在闪"，比美颜的眼睛微抖难看一个
数量级。建议把这套逻辑从 `beauty-filter.c` 抽成共用模块（如 `face-stabilize.h`），
两个滤镜共享。

补充换脸特有的稳定需求：

- 推理结果滞后于当前帧（15fps 推理 vs 60fps 显示）。单纯在旧结果之间插值不能得到当前位姿；
  必须增加轻量级 bbox/关键点跟踪（优先评估光流或上一结果局部跟踪），并将跟踪结果用于当前帧
  仿射更新。跟踪失败时冻结并淡出，而不是继续外推；
- 人脸丢失时结果应淡出而非突然消失。

### 6.4 融合

仿射回贴后需处理边缘接缝：

- P2 阶段：椭圆遮罩 + 高斯羽化（简单，够用）；
- P3 阶段：肤色迁移（匹配目标脸的色调分布）+ 可选泊松融合。

## 8. UI 设计

**不采用**美颜那种"设置里一个复选框 + 自动挂到所有摄像头"的模式
（`ApplyBeautyFilterSetting()`，`OBSBasic.cpp:1466`）。原因：美颜无脸时是 no-op，
无差别挂载没有副作用；风格化涉及"用哪个模型"这个**必选参数**，且用户几乎不会想给所有
摄像头套同一种风格。

采用标准滤镜面板：右键源 → 滤镜 → 添加"AI 人脸风格化"。属性项（已实现）：

- 风格模型（下拉列表，扫描模型目录中除检测器外的 `.onnx`；默认"无（直通）"）
- 融合强度（0-100%）
- 检测频率（10/15/30 fps）
- 执行后端（自动 / CUDA / DirectML / CPU，默认自动；当前仅 CPU 生效）
- 显示检测调试框（默认关闭）

模型列表在打开属性面板时扫描一次，新增模型后需重新打开对话框刷新。

滤镜实例保存自己选择的模型文件名；切换模型时旧 session 在 worker 线程释放并重建，
期间保持直通。

**可选联动（P3+）**：换脸后的人脸区域理应是码率重点，可评估喂给
`obs_encoder_add_roi()`（`libobs/obs.h:2314`）。但滤镜只有源坐标，ROI 接口属于具体 encoder；
实现前必须解决输出/encoder 枚举、多路推流、场景裁剪/旋转/缩放后的坐标映射、encoder 不支持 ROI、
生命周期和与 `motion-roi.cpp` 的优先级协调。未解决这些边界前不得直接从滤镜调用 ROI API。

## 9. 风险

### 技术风险

1. **功耗/调度竞争**（待压力测试确认）：见 §5。笔记本三方争抢 GPU 预算，P0 先埋基础探针，
   P3 才实现依据编码掉帧的自动策略。
2. **模型质量与获取**（当前最大不确定项）：方向变更后没有现成可用的风格模型，需要
   自训练或寻找许可宽松的公开模型。训练数据、训练成本和最终画质都还未验证。
3. **时域抖动**：面部抖动比美颜刺眼得多，§6.3 的稳定化可能需要反复调参。
4. **推理滞后的果冻效应**：15fps 推理 + 60fps 显示，快速运动时贴合会脱节。需要轻量跟踪
   更新当前帧位姿；不能用简单旧结果插值冒充跟踪。**当前未实现**。
5. **ONNX Runtime 的分发**：运行时和 provider DLL 的实际体积、许可证、版本耦合尚未确认，
   打包体积和 `package_portable.ps1` 需要同步调整。
6. ~~**检测器许可证**~~：**已解决**。改用 OpenCV Zoo 的 YuNet（MIT，227KB，可商用），
   SCRFD 降级为可选备选。至此检测链路已无许可证障碍；剩余的许可证风险只在风格模型
   的训练数据与老师模型上（见风险 2）。

### 合规风险

方向变更后风险显著降低：模型不接受源脸输入，无法指定替换为特定自然人，因此不构成
深度伪造工具。但仍建议保留一条约束：

- **处理标记**：水印或流元数据，标明画面经 AI 处理。多数平台对 AI 生成/修改内容有
  披露要求，成本低且能避免审核争议。

此项需业务方决策，不由实现侧默认。

## 10. 验证方案

- **P0 回归**：向 `filter_video` 注入固定的合成帧，比较调用前后各 plane、stride、timestamp 和色彩
  元数据（必须完全一致）；不能比较两次摄像头录制文件，因为输入时序和编码输出不具备确定性；
- **性能**：记录 worker 队列延迟、CPU/GPU 转换、各模型和总处理耗时的 P50/P95/P99，以及显存峰值；
  在"游戏 + NVENC + 换脸"三方负载下同时记录游戏帧率、编码掉帧和推理延迟，不能只看 GPU 利用率；
- **稳定性**：快速转头、侧脸、手部遮挡、进出画面、多人入镜五个场景，人工验收抖动与淡入淡出；
- **降级链**：分别屏蔽 ORT core、provider DLL 或制造 session/run 失败，逐级验证 TensorRT → CUDA
  → DirectML → CPU，以及所有路径失败时的直通兜底；
- **线程安全**：压力下反复启用/禁用、改源脸、改分辨率和销毁滤镜，验证无悬空访问、死锁、数据竞争；
- **格式与几何**：覆盖 I420/NV12/YUY2/YVYU/UYVY、色彩范围/矩阵、镜像/翻转、奇数尺寸、多人和
  跟踪丢失场景，并验证输出格式、stride 和 timestamp 不被破坏；
- **长稳**：连续运行 4 小时，观察显存增长（推理会话的内存泄漏是常见坑）。
